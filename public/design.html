1 Problem and users

New joiners and employees moving teams have no single place that tells them what to complete, in what order, and who must approve them. HR and managers have no simple view of who is waiting on them and how far each person has got.

The goal was a single-browser demo prototype, built in one day and deployed publicly on Vercel, that shows two complete journeys end to end:

Journey A — New Joiner

Register → HR approval → basic onboarding (4 accesses + 4 trainings) → choose team → manager approval → team onboarding (3 + 3) → Completed.

Journey B — Internal Movement

Existing employee requests a new team → new manager approves → new team onboarding → Completed. Current team stays the same until approval.

2 How it was built — spec-driven development with Claude Code

Every stage produced an artifact committed to the repo, and each stage was the input to the next. Claude Code did the writing and building; I approved the plan for each phase and made the product decisions.

  1. Visiondocs/vision.md — roles, both journeys, status model, business rules, 11 acceptance criteria, out-of-scope list.
  2. SpecsGoal, data and frontend specs: data model, 21 business rules (BR1–BR21), every page and its copy.
  3. Open questions8 ambiguities (Q1–Q8), each with a default so work was never blocked, then decided.
  4. Phased plan5 phases, each ending deployable and checked against specific ACs, plus an ordered cut list.
  5. BuildOne commit per phase on main; plan shown and approved before implementing.
  6. TestsVitest unit tests for the rules after every phase; tests + lint + build before each commit.
  7. VercelFirst deploy at the end of Phase 1; every push to main redeploys automatically.

The five phases

  1. Setup, seed data, demo login, registration, HR approval — AC1, AC2, AC3, AC10, first deploy (AC11)
  2. Basic checklists, progress, team-selection unlock — AC4, AC5
  3. Team request, manager approval, team checklists, manager dashboard — AC6, AC7, AC9
  4. Internal movement — AC8
  5. Mobile-width pass, README, screenshots, final deploy
Why specs first? The specs were the source of truth. When a decision changed (e.g. Q8, locking basic items for employees who already have a team), the spec was updated in the same change as the code, so the documents never drifted from the app. Nothing on the cut list had to be dropped.

4 Architecture

All code runs in the browser. Pages never touch storage or change state directly — they call store actions, which run pure functions that enforce the rules.

Store — src/lib/store.ts

External store read with useSyncExternalStore. Server snapshot is null, so pages show "Loading…" until the browser has read storage (no hydration mismatch). Saves the whole state after every action. Syncs other tabs via the storage event.

How the acceptance criteria were verified

  • Unit tests cover the rule behind each criterion: AC2–AC10 are asserted directly (see the table).
  • Demo scripts in goal-spec.md §8 (Script A and Script B) were the manual check for each phase.
  • Headless-browser run of both journeys at 375px and 1280px, locally and on the live URL: checked for horizontal page scroll, tap targets under 40px and console/hydration errors. It found three real bugs that unit tests could not: checklist checkboxes pushed off-screen on phones, screen-reader-only text widening the page, and "Reset demo data" being redirected to /login by the route guard. (The script was a one-off and is not in the repo.)
  • AC11 — the app is live on a public Vercel URL; the headless run used a fresh browser with no login or stored data.

6 Limitations and future work

Limitations

  • Single browser only — data is not shared between browsers, devices or people.
  • No real authentication — anyone can pick any demo user.
  • Checklist completion is self-confirmed and not verified.
  • No notifications — banners on dashboards only.
  • Teams, managers and items are fixed in seed.ts; no admin page.
  • Submitted registrations and requests cannot be edited or withdrawn.

Future work (vision §11)

  • Real authentication / corporate SSO
  • Email notifications for submissions and decisions
  • "Request additional information" status
  • Administrator configuration page
  • Database and multi-user server storage
  • Audit logs, overdue tracking, analytics
  • Integration with real access-management and training systems
  • AI features, e.g. an onboarding help assistant

7 Interview preparation

Ten likely questions, with short answers grounded in the project. Tap a question to open it.

1. Walk me through the project in one minute.

It's an onboarding and internal-movement portal built as a one-day MVP. A new joiner registers, HR approves, they complete 8 basic items, pick a team, the team's manager approves, and they finish 6 team items. An existing employee can request a move; nothing changes until the new manager approves. It's Next.js and TypeScript, data in localStorage, 40 unit tests on the business rules, deployed on Vercel. I built it spec-first with Claude Code: vision, specs, phased plan, then one phase at a time.

2. Why localStorage and not a database?

The brief was a single-browser demo in one day, and a database was an explicit non-goal. localStorage removed all backend work and let one reviewer play every role. I kept it safe to change later: all storage goes through one module, the key is versioned, and bad or old data is reseeded. Swapping in an API would mean replacing store.ts, not the pages or the rules.

3. How do you stop the UI from breaking a business rule?

Rules are enforced in the store actions, not only in the UI. Each action is a pure function that checks its rules and throws a DomainError with a user-facing message — for example, only the target team's manager can decide a request (BR6). The UI hides invalid options too, but the tests call the actions directly, so a rule holds even if the UI has a bug.

4. Why is the overall status calculated instead of stored?

A stored status can drift from the data it summarises. overallStatus() derives it from the registration, completions, pending request and current team using six ordered rules, so it is always consistent. For example, after a move is approved it only counts the new team's items — old completions are kept but no longer count.

5. How did you use Claude Code, and how did you stay in control?

I made it work from documents: the vision, then specs it wrote and I reviewed, then a phased plan. Ambiguities went into an open-questions file with a default for each, and I made the decisions. For every phase it showed a short plan, I approved, it implemented, ran tests, lint and build, committed and pushed. The specs stayed the source of truth and were updated whenever a decision changed.

6. How did you handle unclear requirements?

Each one became a numbered open question with a default that the specs already used, so building was never blocked. Example: a rejected new joiner can't log in, so where do they see the HR comment? Decision Q1: a public status page looked up by request ID. Another, Q8, came up during the build: should existing employees' basic items be locked too? Yes, so the unlock can't be undone.

7. Tell me about a bug you found and fixed.

Clicking "Reset demo data" while logged in sent you to the login page instead of Home. Reset clears the session, so the page's route guard saw no user and redirected to /login, racing the header's own navigation. The fix: the guard only redirects visitors who arrive without access, not users who sign out on the page. Unit tests passed throughout; it was found by running the real journeys in a headless browser.

8. How did you test it, and what would you add?

40 Vitest tests on the pure domain functions, named after the rules and acceptance criteria they check, including both full journeys. On top of that, the demo scripts by hand and a headless-browser run on the live URL at phone width. Next I'd commit that browser run as Playwright end-to-end tests in CI, so UI regressions are caught automatically like the rules are.

9. What would it take to make this production-ready?

Replace localStorage with a database behind an API, and move rule checks to the server so they're actually enforced. Add SSO and real authorisation (today the demo login is just a role switcher), email notifications, audit logs, and an admin page for teams and checklists. Because the rules are already pure functions with tests, they can move to the server largely unchanged.

10. Why didn't you add AI to the product?

I asked the course flowchart question first: does the task need AI? Here it doesn't — every step is a fixed rule, a form or a count, and deterministic code is cheaper, testable and predictable. AI features were also an explicit non-goal for the MVP. I did use AI to build it. A good future fit would be an onboarding help assistant answering questions about procedures, which the vision lists as future work.
